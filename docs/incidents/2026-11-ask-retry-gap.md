# AI 問答重試機制缺失事件(2026-11)

## 發生什麼事

用 AI 工具檢查求職作品集技術報告(PDF)時,發現「核心工程突破與實戰除錯紀錄」表格裡,針對 thought_signature 問題的解決方案寫著:「修正多輪對話間 thought_signature 的保留與傳遞邏輯,並為每輪 API 呼叫加入逾時與重試機制」。但實際檢查 `dashboard/ask/agent.py` 發現 `GeminiLLMClient.generate()` 只有逾時(`http_options` 的 `timeout`),完全沒有重試邏輯——文件寫的功能,程式碼裡其實不存在。

## 根因

PR #147 當初修 thought_signature / 逾時問題時,只實作了逾時保護那一半,重試從未真的寫進程式碼,但文件描述把兩者一起寫成已完成的功能。文件內容後續沒有再對照程式碼實際狀態逐項核對過,落差就這樣留到現在才被抓到。

## 怎麼修的(PR #156)

1. 在 `GeminiLLMClient.generate()` 外包一層 `_generate_with_retry()`,對 `httpx` 逾時跟 Gemini 回傳的 5xx(`ServerError`)做最多 2 次重試(含首次共 3 次嘗試),重試間隔固定 1 秒。
2. 刻意排除 4xx(`ClientError`)不重試——像原本那個「缺少 thought_signature」就是 4xx,重送一樣的請求只會再失敗一次,白白燒 API 額度,對這種必然失敗沒有意義。
3. 新增 4 項測試:逾時後重試成功、5xx 後重試成功、重試用盡後拋出例外、4xx 不重試直接拋出。

## 學到的教訓(供下次專案參考)

- 作品集/技術文件裡描述的「做了什麼」要能對應到實際程式碼,不是規劃或 commit message 寫過「應該要做」就等於做了,寫完文件最好抽空回頭用程式碼逐項核對一次。
- 用 AI 工具反向核對「文件 vs 程式碼」是低成本、有效抓出這種落差的方法,值得養成習慣,尤其是求職作品集這種會被仔細檢視的文件。
- 重試機制要分清楚「暫時性失敗」(逾時、5xx)跟「必然失敗」(4xx 錯誤請求),對必然失敗重試只是浪費資源,不會真的解決問題。

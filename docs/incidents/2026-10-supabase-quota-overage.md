# Supabase 免費額度超標事件(2026-10)

## 發生什麼事

2026-10 收到 Supabase 通知信:組織用量超過 Free Plan 額度,若維持現狀,2026-11-17 起專案將被限制存取。登入 Usage Dashboard 確認:

- **Egress**(資料傳輸量):6.01 / 5 GB,超標 120%
- **Log Ingestion**(日誌寫入量):1.983 / 1 GB,超標 198%
- Database Size、Monthly Active Users、Cached Egress 皆正常

## 根因

`dashboard/app.py` 有一個背景快取預熱迴圈(`_warm_cache_loop`),在 `app.on_startup` 註冊,**只要 Render 服務在跑就 24 小時不間斷執行**,跟有沒有訪客完全無關。問題出在三個地方疊加:

1. **間隔太短**:`CACHE_WARM_INTERVAL = 25`(秒),比 ESP32 實際上傳資料的頻率(60秒一次)還快,每一輪都在重抓幾乎沒變化的同一批資料。
2. **預熱了最貴的查詢**:每輪都對每台裝置呼叫 `load_history(did, 24)`(抓24小時原始遙測,可能上千筆)和 `load_forecast_eval`(自己註解就寫明是檔案裡最慢的查詢,要翻歷史資料去比對預測),這兩個是迴圈裡最吃資源的呼叫。
3. **全天候執行**:一個求職作品集展示網站,凌晨根本不會有人看,卻也照常每25秒跑一輪。

估算:改之前一天約跑 **5萬多次 API 請求**(25秒一輪 × 每輪10幾個查詢 × 全天),這直接撐爆了 Egress(資料量)跟 Log Ingestion(每次 API 請求 Supabase 平台都會記一筆日誌)。

## 怎麼修的(PR #140 / #141 / #142)

1. `CACHE_WARM_INTERVAL` 25秒 → 180秒
2. 從背景預熱清單移除 `load_history`(24h)、`load_forecast_eval` 這兩個最貴的查詢——改成訪客真的點開對應頁面時才現抓(代價是多等1–2秒,可接受)
3. 加入 `WARM_ACTIVE_HOURS = range(8, 24)`,凌晨0–8點(Asia/Taipei)整段跳過背景預熱

三項疊加後,請求量估計砍到原本的 **1/20 以下**。

## 學到的教訓(供下次專案參考)

- **背景常駐迴圈最容易被忽略**:它不像使用者操作那樣「看得到流量來源」,是最隱形的額度殺手,寫的時候容易只想著「讓使用者體驗更好」卻忘了算背景成本。
- **預熱/輪詢頻率要對齊「資料實際更新速度」,不是「越快越新鮮越好」**:資料源頭60秒才更新一次,預熱卻設定25秒一輪,等於大部分請求都在做白工。
- **免費方案的額度要主動設提醒,不要等到被動收到警告信**:這次是收到 Supabase 的 email 才發現,中間可能已經悄悄超標好一段時間。
- **「背景永遠熱」是一種預先付出的成本,要evaluate是否值得**:犧牲少數訪客的1–2秒冷啟動等待,換取24小時零成本,對低流量的展示型網站通常划算。
